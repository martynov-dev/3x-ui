# Бэкапы: компьютер, роутер и другой сервер

[English](full-backups.md) | [Русский](full-backups.ru.md)

## Скачать на компьютер без консоли

1. Откройте панель → **Бэкапы и сайт → Полные бэкапы**.
2. Нажмите **Создать бэкап сейчас** и дождитесь результата.
3. В таблице **Сохранённые архивы** нажмите на имя архива. Браузер скачает его на ваш компьютер.
4. Убедитесь, что скачался файл `.tar.gz`, а не страница входа. Сохраните его в личной папке с ограниченным доступом: внутри есть пароли и приватные ключи.

Это ручное скачивание. Веб-страница не может автоматически сохранять архивы на выключенный компьютер.

## Включить расписание

1. Включите **Автоматические бэкапы**.
2. Укажите интервал в часах: `24` — раз в сутки, `168` — раз в неделю.
3. Укажите количество **локальных** копий, например `7`.
4. Нажмите **Сохранить**. Первый бэкап запускается в течение минуты; затем — через выбранный интервал. После изменения настроек ранее успешного расписания сохраняется отсчёт от последней попытки.
5. Проверьте **Последний успешный бэкап** и список архивов. Если страница уже открыта, нажмите **Обновить**.

Расписание работает при запущенной панели. Архив всегда сначала создаётся на сервере панели, обычно в `/etc/x-ui/full-backups`. SSH-отправка сохраняет ещё одну копию на другом устройстве. Старые удалённые копии автоматически не удаляются.

Стандартные пути nginx, сайта и сертификатов уже заполнены в **Дополнительных путях**. База и файлы панели включаются всегда. Нестандартные каталоги добавляйте отдельными строками. Архив не является образом операционной системы.

## Автоматически отправлять на другое устройство

Для этого нужны SSH/SFTP, вход по ключу и существующая папка с правом записи. На принимающем устройстве должна работать POSIX-команда `mv`. Подходят Linux-сервер и подготовленный OpenWrt. Обычная SSH-оболочка Windows пока не поддерживается.

**Однократная подготовка сейчас требует консоли или помощи администратора.** В панели ещё нет мастера создания ключей и подключения хранилища. После подготовки расписание и отправка настраиваются через интерфейс.

Сначала обеспечьте сетевую доступность. Адрес домашнего роутера `192.168.1.1` недоступен обычному VPS через интернет. Используйте уже настроенную VPN-связь между сервером и домашней сетью и адрес, доступный через неё. Не нужно открывать административный SSH роутера всему интернету. Принимающий компьютер должен быть включён во время отправки.

### 1. Создать отдельный ключ на сервере панели

Для обычной установки на Ubuntu/Debian выполните **на сервере панели**:

```bash
sudo -i
apt-get update
apt-get install -y openssh-client
install -d -m 700 /root/.ssh
test -f /root/.ssh/backup_ed25519 || ssh-keygen -t ed25519 -N '' -f /root/.ssh/backup_ed25519
cat /root/.ssh/backup_ed25519.pub
```

Скопируйте полученную строку `ssh-ed25519 ...`. Это публичная часть ключа. Файл без `.pub` оставьте на сервере панели.

### 2а. Принимающий Linux-сервер

На **принимающем сервере Ubuntu/Debian** один раз выполните:

```bash
sudo apt-get update
sudo apt-get install -y openssh-server
sudo adduser --disabled-password --gecos '' backup
sudo install -d -o backup -g backup -m 700 /home/backup/.ssh
sudo install -d -o backup -g backup -m 700 /srv/backups/3x-ui
```

Если пользователь `backup` уже существует, повторно создавать его не нужно. Добавьте скопированный публичный ключ в `/home/backup/.ssh/authorized_keys`, по одному ключу на строке. Не затирайте существующие ключи. Затем:

```bash
sudo chown backup:backup /home/backup/.ssh/authorized_keys
sudo chmod 600 /home/backup/.ssh/authorized_keys
sudo systemctl enable --now ssh
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Запишите отпечаток сервера для следующего шага.

### 2б. Роутер Banana Pi R4 с OpenWrt и SD-картой

Эти шаги относятся именно к OpenWrt; наличие Banana Pi само по себе не определяет установленную ОС.

1. В LuCI откройте **Система → Точки монтирования / System → Mount Points**. Убедитесь, что раздел SD-карты смонтирован и подключается после перезагрузки. Пример точки монтирования: `/mnt/backups`. Не форматируйте раздел с уже нужными данными.
2. В **Система → Программное обеспечение / System → Software** установите `openssh-sftp-server`, если его нет. Он добавляет SFTP для стандартного SSH-сервера Dropbear.
3. В **Система → Администрирование → SSH-ключи / System → Administration → SSH-Keys** добавьте публичный ключ сервера панели. В стандартной конфигурации OpenWrt это доступ пользователя `root`; ключ предоставляет административный доступ к роутеру.
4. На роутере проверьте `df -h /mnt/backups`: путь должен находиться на SD-карте, а не во внутренней памяти. Только после этого создайте каталог:

   ```sh
   mkdir -p /mnt/backups/3x-ui
   chmod 700 /mnt/backups/3x-ui
   ```

5. Проверьте доступность SSH роутера с сервера панели через вашу VPN-связь. Отпечаток SSH-ключа сверьте с ключом роутера через доверенное локальное подключение. Для Dropbear публичную часть можно посмотреть командой `dropbearkey -y -f /etc/dropbear/dropbear_ed25519_host_key`, если используется этот файл ключа.

Документация OpenWrt: [монтирование накопителей](https://openwrt.org/docs/guide-user/storage/fstab), [SFTP](https://openwrt.org/docs/guide-user/services/nas/sftp.server), [Dropbear](https://openwrt.org/docs/guide-user/base-system/dropbear). Названия пунктов LuCI зависят от версии и языка.

### 3. Проверить устройство с сервера панели

Вернитесь на **сервер панели**. Пример для Linux-получателя; замените адрес и порт своими:

```bash
ssh -p 22 -i /root/.ssh/backup_ed25519 backup@backup.example.com
```

При первом подключении сравните показанный отпечаток с проверенным на предыдущем шаге. Подтвердите только совпадающий ключ. Это запишет его в `known_hosts`. Выйдите командой `exit`, затем проверьте неинтерактивный доступ:

```bash
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -p 22 -i /root/.ssh/backup_ed25519 backup@backup.example.com 'test -d /srv/backups/3x-ui && test -w /srv/backups/3x-ui && command -v mv'
```

Для роутера замените пользователя на `root`, адрес на его доступный через VPN адрес, каталог на `/mnt/backups/3x-ui`.

### 4. Заполнить форму в панели

Раскройте **Удалённая копия по SSH** и заполните:

| Поле | Другой Linux-сервер | Роутер OpenWrt |
|---|---|---|
| Адрес SSH | `backup.example.com` | Доступный с панели адрес роутера |
| Пользователь | `backup` | `root` в стандартном OpenWrt |
| Порт | `22` или ваш порт | Порт SSH роутера |
| Каталог | `/srv/backups/3x-ui` | `/mnt/backups/3x-ui` |
| Приватный ключ | `/root/.ssh/backup_ed25519` | `/root/.ssh/backup_ed25519` |

Нажмите **Сохранить**, затем **Создать бэкап сейчас**. Проверьте отсутствие ошибки и наличие окончательного `.tar.gz` на принимающем устройстве. Пока файл передаётся, у него суффикс `.partial`. Если отправка не удалась, локальный архив остаётся доступен для скачивания. Очистка адреса SSH и сохранение отключают отправку.

### Компьютер Windows или Linux

- **Любой компьютер, без консоли:** скачивайте архив по ссылке в панели.
- **Linux-компьютер, автоматически:** настройте как принимающий Linux-сервер выше. Компьютер должен быть включён и доступен с панели.
- **Windows, автоматически:** стандартный Windows OpenSSH пока не поддерживается из-за команды завершения передачи. Можно использовать отдельную Linux-VM с SSH и постоянным диском, но её сеть и автозапуск требуют подготовки. Для первого теста проще ручное скачивание.

### Если сама панель работает в Docker

Ключ и `known_hosts` должны существовать **внутри контейнера панели**. Подключите их отдельным постоянным томом, например `/root/.ssh`, с доступом только администратору. SSH-клиент включён в образ форка. Каталоги nginx и сайта также должны быть доступны контейнеру, иначе он не сможет их редактировать и архивировать. Обычный контейнер панели не управляет nginx на хосте автоматически.

## Как проверить, что бэкап годится для восстановления

Скачайте архив, затем на отдельной машине с той же версией Ubuntu/Debian и архитектурой выполните проверку через `setup.sh --backup /path/full-backup.tar.gz --check`. После этого проверьте реальное восстановление на чистой тестовой машине. Автовосстановление поддерживает полные Linux-бэкапы SQLite этого форка; PostgreSQL и Docker/Alpine требуют другого процесса. DNS, внешние firewall и внешние сервисы архив не восстанавливает.

`setup.sh` и релизы должны быть опубликованы в вашем форке; до слияния `dev` в `main` используйте файлы текущей ветки. Подробности и команды восстановления — в [README](../README.ru_RU.md).

### Проверенный сценарий на VM

20 октября 2026 года проверена установка и восстановление между двумя отдельными чистыми Ubuntu 24.04.5 LTS (amd64, SQLite) с настоящим systemd:

- Установка через `setup.sh`, запуск панели и nginx, вход в панель.
- Создание сайта через API панели под ограничениями штатного systemd-сервиса, HTTP и сертификат из отдельного каталога.
- Полный бэкап и доставка по SSH с совпадающим SHA256.
- `--check` без установки панели/nginx, затем полное восстановление на второй VM.
- Сохранность входа, настроек расписания и получателя, SSH-ключа, бинарника, сертификата и тестового inbound Xray; работа HTTP/HTTPS и прослушивание порта Xray.
- Повторная отправка бэкапа после восстановления без настройки SSH заново.
- Обновление через `update.sh` с сохранением входа, настроек, сайта и работающей отправки по SSH.
- Автоматическое создание и доставка бэкапа восстановленным планировщиком: только в тестовой базе время последней попытки сделано просроченным, запуск выполнял штатный планировщик панели.

При обновлении штатный `update.sh` заменяет слишком короткий путь панели (например `/`) случайным и выводит новый URL. Это нужно учитывать отдельно от переноса учётных данных.

Для ещё не опубликованной сборки использовался локальный архив релиза; только загрузки файлов форка перенаправлялись на тестовый HTTP-сервер. Загрузка опубликованного GitHub-релиза этим прогоном не проверялась. Debian, другие версии ОС/архитектуры, PostgreSQL и восстановление рабочего VPN-трафика этим прогоном также не проверялись. Логи и тестовый архив сохранены локально в `.cache/vm-test/`; архив содержит тестовый приватный ключ.
